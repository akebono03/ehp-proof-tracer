# Phase 171 R2J-R4-R9-R15 — Root 分岐別 Blocker 監査

## 監査の目的

R14 は $\pi_6^3$ の公開探索で Root Expansion 4件、Resolver 67回、循環依存12件、`no_derivation` 発生29件を報告した。しかし29件は未証明命題29種類を意味せず、Root のどの経路に関係するかもコマンド出力だけでは確定できない。

R15 は **R14 の実行結果の再集計のみ**を行い、特定の推論規則や証明探索器を修正しない。

## 変更対象と位置

- 既存ソースファイル／既存 import／クラス／関数／テスト：変更なし。
- 新規 `phase171_r2j_r4_r9_r15_branch_blocker_audit/__init__.py`。
- 新規 `audit.py`：最初に import と定数を定義し、その直後に `git_read`, `blob_sha`, `normalize`, `preflight`, `checked_r14_report`, `matches_goal`, `candidate_observation`, `route_signature`, `analyze_r14`, `main` を順番に追加する。
- 新規 `tests/__init__.py` および `tests/test_audit.py`：必要な import の直後に `_fixture_r14` 相当の関数（実装名 `fixture_r14`）と6件のテスト関数を追加する。
- 新規 `run.ps1`, `README.md`, `監査仕様.md`, `CODE_FULL_JA.md`。

全ソースコードとテストコードは `CODE_FULL_JA.md` に省略せず掲載する。

## 監査手順

1. `develop` ブランチ、HEAD、既存 R11 Provider の Git Blob SHA、ローカル作業ファイルとの一致を確認する。
2. R14 の `output/audit.json` の Phase、監査種別、未変更フラグ、イベント欠落の有無を照合する。
3. Root Provider の4件を元の順序のまま取り出し、Root フレームへ伝播した失敗と照合する。
4. R14 の `origin=True` かつ `kind=no_derivation` のイベントを、Goal の種別と保存された `repr` で集約する。
5. 各未証明 Goal について、同じ R14 レポートに記録された Provider 呼出結果を突き合わせる。
6. `NO_EXPANSION`、`PROPOSALS_UNPROVED`、`NOT_OBSERVED` に分類し、頻度の高いものを表示する。
7. Git の追跡対象の状態が監査前後で不変であることを確認し、`output/audit.json` に監査レポートを出力する。

## 解釈上の制約

- `origin_counts` は元の例外発生回数であって相異なる Goal 数ではない。
- Provider の `repr` は R14 時点で長さ制限されている。R15 の照合結果は診断用であり、数学的に同じ命題かどうかの証明ではない。
- Root への伝播例外数は各経路の失敗観測であり、すべての前提が失敗したことを意味しない。
- `NOT_OBSERVED` を `NO_EXPANSION` と扱わない。
- 新しい `GIVEN`、既存の完成 Proof Tree の流用、数学的規則の追加、循環拒否の緩和、証明一意性条件の緩和、Trust Boundary の変更はしない。
- R15 は既存の R14 JSON を集計するのみで、`complete` や Web 検証済みへの状態変更を行わない。
