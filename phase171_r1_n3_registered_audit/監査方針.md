# Phase 171 R1 — n=3 登録済み群の証明状態監査

## 目的・監査境界

Phase 170 では $n=2,\ 1\le k\le33$ の33群で既存の型付き Proof Search と標準 Web 経路の完成が検証された。Phase 171 R1 では、次の依存関係を調べるため、$n=3$ の登録済み群の現状を測定する。この R1 では本番の証明規則、Toda 命題登録、DB、Renderer、既存テスト、正式5文書を変更しない。

`data/sphere.csv` の GitHub `develop` 版では $n=3$ に70データ行があり、重複を除いた座標 $k=0,1,\ldots,33$ の34群が存在する。登録行数をそのまま群数とはみなさない。$k=0$ の $\pi_3^3$ も監査対象とし、$k<0$ は本監査の範囲外とする。

## 対象の実装と既存テスト

現行 HEAD `715b00d67d4b3ff4b34bf87229842d14960ea6bb` の `phase165_r55_nk_only_goal.py`、`web_group_proof.py`、`phase170_r3_r8_n2_exhaustive_audit/audit.py`、Toda (5.2) と (7.12) の関連登録コード・データを確認した。Phase 170 R3-R10R1 の監査契約テストも確認し、各群の探索結果と Web の完成判定を分離する方針を引き継ぐ。出典や先行 DB の採用判断は既存探索経路に委ねる。

## 監査手順

1. `develop` のローカル・リモート HEAD、追跡済み作業ツリーの CLEAN、現行コード6ファイルの Git blob、DB の対象座標を検証する。
2. 対象34群を各別の Python 子プロセスで実行する。Windows の文字コード問題を避けるため、`PYTHONIOENCODING=utf-8` と `PYTHONUTF8=1` を設定する。
3. `exact_prior_database_result(3,k)` で DB Goal の型付き取得を観測し、`search_group_from_registered_goal(n=3,k=k)` の結論、ステップ、未解決 Goal、diagnostics、使用 GIVEN locator を記録する。
4. `build_standard_web_group_proof_view(n=3,k=k,max_depth=2,mode="narrative",citation_source="model")` を実行し、`generic-complete-proof`・`partial_result=False`・有効な表示行が得られたか検査する。
5. `audit.json`・`audit.md`・各群の `k_XXX.log` を Recovery に保存する。監査中に追跡済みファイルが変更されていないことを再検査する。

## 結果の読み方

`COMPLETE_AND_WEB_VERIFIED` は完成の観測結果、`PROOF_UNFINISHED` は探索の不足、`DB_GOAL_UNTYPED_OR_MISSING` は DB 目標の不足、`WEB_NOT_VERIFIED` は公開検証の問題を示す。Worker 例外・タイムアウトは証明不足と混同せず別集計する。**34件がすべて完成することは R1 の完了条件ではない。** R1 の完了条件は34件の現状を欠落なく記録し、次に検証すべき未完成群・欠落する前提を特定することである。

全体 pytest は Phase 171 の最後にのみ行う。数学的な不足が具体化するまでは将来 Phase の規則を追加せず、`HyoujiGen.csv` にない生成元同一性を推測で補わない。
