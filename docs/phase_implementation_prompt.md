# Phase Implementation Prompt

この文書は、`ehp_proof` / `ehp-proof-tracer` の各 Phase を実装するときに、
ChatGPT / Codex へコード変更を依頼するための共通プロンプトです。

原則として、各 Phase ではこのテンプレートの

- Phase 名
- 実装内容
- 目的
- 必要に応じた補足条件

だけを書き換えて使用します。

---

# Phase 実装依頼

現在のコード、関連テスト、既存ドキュメントを確認したうえで、次の Phase を実装してください。

## 今回の Phase

**Phase X-X：［ここに実装内容を書く］**

目的：

［この Phase で実現したいことを書く］

必要に応じて補足：

- ［今回特に維持したい仕様］
- ［今回追加したい API / behavior］
- ［今回対象外にしたい内容］

---

## 基本方針

まず現在の実装と関連テストを確認し、今回変更する必要がある箇所を特定してください。

既存設計をできるだけ維持し、今回の Phase に必要な最小限の変更だけを行ってください。

今回の Phase に関係しないリファクタリングは行わないでください。

まだ次の Phase 以降で扱う予定の機能を先取りして実装しないでください。

既存 API、既存データモデル、既存テストとの backward compatibility が必要な場合は維持してください。

同じ処理を行う既存 helper、既存 abstraction、既存 data model がある場合は、可能な限り再利用してください。

---

## 実装前に必ず確認すること

コードを書く前に、まず以下を簡潔に整理してください。

1. 現在の関連実装
2. 今回変更するファイル
3. 今回変更するクラス
4. 今回変更する関数・メソッド
5. 新しく追加するクラス・関数・メソッド
6. 変更が必要な import
7. 今回は変更しない部分
8. 実装方針
9. 既存 API への影響
10. 既存テストへの影響

この確認後に、実際のコードを提示してください。

---

# コード提示ルール

## 1. 差分数行ではなく「置き換え可能な単位」で提示する

修正コードを提示するときは、変更箇所の数行だけを示すのではなく、
そのままコピー＆ペーストして置き換えられる単位で全文を提示してください。

原則として以下の単位で提示してください。

### import を変更する場合

そのファイルの **変更後の import 部分全体** を提示してください。

新しい名前を使用する場合は必ず、

1. どのモジュールから import するか
2. 既存 import のどこが変わるか
3. 変更後の import 部分全体

を明示してください。

「既存コードですでに import 済み」という理由で説明から省略しないでください。

---

### クラスを変更する場合

**そのクラス全体** を提示してください。

クラス内のメソッドを1つだけ変更する場合でも、
変更がクラス全体の構造や field 定義と密接に関係する場合は、
クラス全体を提示してください。

---

### 関数を変更する場合

**その関数全体** を提示してください。

関数内部の変更行だけを抜き出さないでください。

---

### メソッドを変更する場合

原則として **そのメソッド全体** を提示してください。

ただし、変更が dataclass field、constructor、class-level configuration などと関係する場合は、
必要に応じてクラス全体を提示してください。

---

### 新しいクラス・関数・メソッドを追加する場合

追加するコード全文を提示し、

- どのファイルに追加するか
- どのクラス／関数の前に追加するか
- どのクラス／関数の後に追加するか

のいずれかで **追加位置を明示** してください。

---

### テストを追加・変更する場合

追加・変更する **テスト関数全体** を提示してください。

import の追加・変更が必要なら、
テストファイルの変更後 import 部分全体も提示してください。

fixture や helper を新規追加する場合も、その定義全体を提示してください。

---

## 2. コードを省略しない

コード内で以下のような省略をしないでください。

```python
...
```

```python
# existing code
```

```python
# unchanged
```

コピー＆ペースト対象となるクラス、関数、メソッドについては、
実際に必要なコードを全文提示してください。

---

## 3. ファイル全文は原則不要

修正対象ファイル全体を毎回提示する必要はありません。

原則として、

- import 部分
- クラス単位
- 関数単位
- メソッド単位
- テスト関数単位

で提示してください。

ただし、変更範囲がファイル全体に及ぶ場合や、
ファイル全体を提示した方が安全な場合は、その理由を明示したうえで全文提示して構いません。

---

# 修正箇所の提示形式

変更箇所ごとに、原則として次の形式で示してください。

## 1. `path/to/file.py`

### 変更対象

`ClassName.method_name()`

または

`function_name()`

または

`ClassName`

### 変更理由

［なぜこの変更が必要なのかを簡潔に説明］

### import の変更

必要な場合のみ記載してください。

```python
# 変更後の import 部分全体
```

### 置き換えるコード

```python
# クラス・関数・メソッドの全文
```

### 追加位置

新規追加の場合のみ、

- `foo()` の直後
- `Bar` クラスの前
- import ブロックの直後

など、位置を明示してください。

---

## 2. `path/to/another_file.py`

同じ形式で続けてください。

# テスト方針

今回の Phase の仕様を確認するための pytest を追加または更新してください。

テストを提案するときは、まず以下を整理してください。

1. 何を確認するテストか
2. なぜそのテストが必要か
3. 既存テストでは不足している点
4. regression test として何を防ぐか

既存テストですでに十分確認できている内容については、
不要な重複テストを追加しないでください。

---

## テストコードの提示

テストについても次を必ず提示してください。

- 対象テストファイル
- 必要な import
- 追加または変更するテスト関数全体
- 必要な fixture / helper 全体
- 追加位置

例：

## `tests/test_xxx.py`

### import

```python
# 変更後 import 全体
```

### 追加するテスト

```python
def test_xxx():
    ...
```

### 追加位置

`test_yyy()` の直後に追加。

---

# 実装上の制約

以下を守ってください。

- 現在の API を不必要に壊さない
- 既存テストを通す
- 今回の Phase に必要な最小限の変更にする
- Phase に関係しないリファクタリングをしない
- 将来 Phase の機能を先取りしない
- 型・データモデル・命名を現在のコード設計に合わせる
- 既存 helper を可能な限り再利用する
- backward compatibility が必要な API は維持する
- unnecessary abstraction を追加しない
- unnecessary dependency を追加しない
- コード内で `...` による省略をしない
- import を暗黙扱いしない
- テストだけ通すための special case を入れない
- domain logic と generic inference engine の責務境界を維持する
- 既存の Phase で確立した設計方針を理由なく変更しない

---

# `ehp_proof` 固有の注意

このプロジェクトでは、
generic inference engine と EHP domain-specific inference rules の責務を分離してください。

generic engine に入れるべき一般的な処理と、
EHP 固有 rule に属する処理を混同しないでください。

特に、

- pattern matching
- shared binding consistency
- conclusion substitution
- fixed-point inference
- inference history
- duplicate handling

など generic engine 側ですでに存在する機能は、
EHP rule 側で独自再実装しないでください。

一方、

- EHP exactness
- E / H / P map に関する domain rule
- sphere homotopy group に固有の条件
- EHP sequence に依存する数学的条件

は domain-specific layer に置く方針を基本としてください。

既存コードを確認し、現在の設計境界を優先してください。

# 実装後に必ず示すこと

実装コードの提示後、最後に以下をまとめてください。

## 1. 変更一覧

例：

- `ehp_proof/proof.py`
  - import
  - `InferenceRule`
  - `apply_inference_match()`
- `ehp_proof/ehp_rules.py`
  - `EHPExactnessRule`
- `tests/test_ehp_rules.py`
  - `test_xxx()`

のように、変更した単位を列挙してください。

---

## 2. 実行するテスト

今回の Phase を直接確認するテストをまず示してください。

```powershell
python -m pytest tests/対象テスト.py -v
```

必要なら関連 regression test も示してください。

最終確認として full test suite が必要なら、

```powershell
python -m pytest -v
```

も示してください。

---

## 3. 期待されるテスト結果

追加したテストについて、
何が pass すれば今回の仕様を満たしたと判断できるかを簡潔に説明してください。

---

## 4. この Phase の完了条件

今回の Phase が完了したと判断できる条件を箇条書きで示してください。

例：

- 新しい rule が想定する premise に match する
- bindings が conclusion に正しく substitution される
- derived relation が proof に追加される
- duplicate derivation が既存仕様どおり処理される
- 既存テストが regression しない

---

## 5. 次の Phase との境界

今回実装した範囲と、
次の Phase に残すべき内容を明確にしてください。

特に、
「今回実装していないもの」を明示してください。

これにより Phase の責務が肥大化しないようにしてください。

---

# 出力順序

最終的な回答は原則として以下の順序にしてください。

1. 現状確認
2. 今回の変更方針
3. 変更ファイル一覧
4. 各ファイルの import 変更
5. 各クラス／関数／メソッドの置換コード
6. テストコード
7. 実行コマンド
8. 期待結果
9. Phase 完了条件
10. 次 Phase との境界

---

# 使用例

以下のように冒頭だけ差し替えて使用します。

```text
現在のコード、関連テスト、既存ドキュメントを確認したうえで、
次の Phase を実装してください。

Phase 6-4：XXXXXXXX

目的：
XXXXXXXX を実現する。

以下は docs/phase_implementation_prompt.md のルールに従ってください。
```

または、この文書全体をプロンプトとして貼り付け、
`Phase X-X` と目的だけ書き換えて使用してください。

---

# 運用方針

各 Phase では、

1. 小さな機能単位で実装
2. 対応テストを追加
3. pytest を確認
4. README / `docs/design.md` / `docs/development_log.md` を必要に応じて更新
5. Phase 完了
6. 次 Phase へ進む

という流れを基本とします。

コード変更時には、
「どこを書き換えるか分からない断片コード」ではなく、
**import を明示したうえで、クラス・関数・メソッド単位の完全な置換コード**
を得ることを最優先とします。
